# Coding Standards

Repo-wide code conventions for `lib/`. Read before changing code.

## Language and framework

- Dart with Flutter; the SDK is pinned by `.fvmrc` (see `docs/developer-guide.md`).
- `flutter analyze` must be clean — the lint set is `analysis_options.yaml` (`flutter_lints`). Never weaken a lint to land code.
- No new dependencies without explicit user approval. Adding one means editing `pubspec.yaml` and saying why in the change.
- Leave the platform scaffolding (`android/`, `linux/`, `macos/`, `windows/`) alone unless the change is about the platform layer itself.

## App identity (hard rule)

One product, one identity. A name or id change lands on every platform in the same change:

| Surface | Where |
| --- | --- |
| Android label, package id | `android/app/src/main/AndroidManifest.xml` (`android:label`), `android/app/build.gradle.kts` (`namespace`, `applicationId`), the Kotlin package directory |
| Linux app id, window title | `linux/CMakeLists.txt` (`APPLICATION_ID`), `linux/runner/my_application.cc` (header-bar and window titles) |
| macOS product name, bundle id | `macos/Runner/Configs/AppInfo.xcconfig` (`PRODUCT_NAME`, `PRODUCT_BUNDLE_IDENTIFIER`), `macos/Runner.xcodeproj/project.pbxproj` (product reference path, `TEST_HOST`, `RunnerTests` bundle id) |
| Windows window title, version strings | `windows/runner/main.cpp` (window title), `windows/runner/Runner.rc` (`FileDescription`, `ProductName`) |
| In-app title | `lib/main.dart` (`MaterialApp.title`) |

Current identity: display name **Geergit Root Helper**, application id **`com.geerxlabs.geergitroothelper`**.

## Layout

- `lib/` — application code; entry point `lib/main.dart`. Organize by feature folder (`lib/<feature>/…`) once a second screen exists; shared widgets in `lib/widgets/`, pure helpers in `lib/utils/`.
- `test/` — widget and unit tests, mirroring `lib/` paths.
- `android/`, `linux/`, `macos/`, `windows/` — platform runners generated by `flutter create`.
- `docs/` — agent instructions, ADRs, plans, specs (see `docs/AGENTS.md`).

## Widgets

- Prefer `const` constructors and small single-purpose widgets; extract at the second identical use.
- Keep platform-specific behavior behind an explicit check (`Platform.isAndroid`, …) instead of forking the widget tree.
- Give widgets that automation or tests must target a stable `Key` — never an index or a translated label.

## Documentation

- Docs before code: document the decision or lesson before implementing it; update the existing doc before creating a new one.
- New ADRs → `docs/adr/NNNN-title.md`; plans → `docs/plans/`; interface specs → `docs/specs/`.
- Update the nearest `AGENTS.md` and refresh affected Child DOX Index entries after structural change.

## Verification

```bash
flutter analyze
flutter test
flutter build linux --debug   # or: flutter build apk --debug
```

- UI changes: verify on a running target, not only in a widget test — see "Verifying a build" in `docs/developer-guide.md`.
- Commit and push after every task; stage explicit paths (`git add <paths>`), never `git add -u`.
